Les coordonnées du payeur sont désormais contrôlées avant de créer une commande boutique ou une inscription au tournoi. Les erreurs apparaissent sous les champs, avec les mêmes règles côté serveur. L’administration permet aussi d’exporter les commandes filtrées en CSV et de regrouper leurs bons fournisseur dans un PDF unique.

La [spécification officielle HelloAsso](https://github.com/HelloAsso/helloasso-open-api/blob/1fe7b01be00cce09c7b1a134be27fbcaf87bb43e/helloasso.json) limite prénom, nom et e-mail à 255 caractères, sans interdiction publiée des parenthèses. Le site conserve ses limites plus courtes et accepte les noms accentués, composés et internationaux. Il refuse les coordonnées vides, les contrôles invisibles, les adresses e-mail mal formées et les téléphones sans assez de chiffres. Le rôle, le club et la catégorie sont distingués du nom du payeur dans le formulaire.

Les refus HelloAsso conservent désormais le statut HTTP et les seuls identifiants de champs reconnus, affichés dans l’administration boutique et tournois. Aucun message brut ni valeur du payeur n’est enregistré. Les anciennes erreurs restent sans détail. Les commandes existantes conservent leur empreinte de reprise, leurs articles et leurs montants ; un paiement déjà actif ou payé suit le parcours antérieur. Aucun paiement n’est relancé automatiquement. Les contraintes et leurs sources sont détaillées dans `docs/HELLOASSO-COORDONNEES.md`.

- CSV : une ligne par commande, avec les colonnes en français, les coordonnées, les états de préparation et de paiement, les articles, tailles, couleurs, personnalisations, quantités et montants. Le fichier utilise le séparateur point-virgule, les décimales françaises et un marqueur UTF-8 pour Excel. Les guillemets et retours à la ligne des personnalisations sont conservés et les débuts de cellules interprétables comme formules sont neutralisés.
- PDF : tous les bons des commandes payées et non annulées correspondant à la recherche sont réunis dans un fichier, avec une nouvelle page par commande client et une pagination globale. Le téléchargement individuel reste disponible. Les coordonnées privées du client et les prix de vente restent exclus des données fournisseur.
- La liste et les exports partagent le même filtre SQL. Les exports parcourent les résultats par lots avec un curseur stable, y compris lorsque plusieurs commandes ont la même date. Le téléchargement ne modifie pas l’état des commandes et n’envoie aucun mail. Une erreur interrompt l’export sans télécharger de fichier partiel.

Aucune migration de base. Le déploiement prépare désormais les points de restauration natifs D1 Time Travel de DB, ORDERS et TOURNAMENTS avant les migrations et la publication du Worker. Ils sont datés au même instant, chiffrés avec le secret existant `PRODUCTION_ARCHIVE_PASSWORD`, déchiffrés et vérifiés, puis conservés dans un artefact GitHub pendant 7 jours. Le déploiement est bloqué si cette préparation ou sa conservation échoue. L’artefact contient les repères de reprise, pas des dumps SQL ; la restauration dépend de la rétention Time Travel de l’offre Cloudflare. L’export SQL complet peut rendre D1 indisponible : il reste réservé à une opération de maintenance explicite.

Validation : 220 tests, TypeScript, build et analyse du workflow réussis. Dans Chromium, les cinq boutiques et le formulaire tournoi refusent les saisies invalides avant toute commande ; un HTTP 400 simulé indique le champ reconnu et une reprise conserve une commande unique. Les tests protègent également les anciennes commandes payées et les demandes déjà actives. Les exports ont été exécutés dans le Worker avec SQLite strictement en lecture seule, un paiement existant et une file de mails : toutes les tables restent identiques, sans appel externe ni tâche de fond. Les points de reprise, le chiffrement, le déchiffrement et les blocages du déploiement sont testés localement. Téléchargement également vérifié dans Chromium d’un CSV de 63 commandes et d’un PDF de 61 bons éligibles depuis la page 2. Aucun paiement ni envoi réel. Les points réels Cloudflare seront préparés par GitHub Actions au prochain déploiement ; ils n’ont pas été obtenus depuis cet environnement.
